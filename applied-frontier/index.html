Serving DeepSeek-V3 and Training DeepSeek-V4

Part 16 of How to Scale Your Model: The 2026 Update (Part 15: Training in 2026 | 2026 Update: Outline)

In the spirit of Sections 6 and 8, we take a real model and real hardware and work the numbers. DeepSeek published the configuration, throughput and cost of its production serving system for V3 and R1 on H800s, which makes it the only frontier deployment whose numbers we can check against the rooflines of Sections 13 and 14. We do that, then ask what changes on a GB200 NVL72, and finally what it would take to pretrain a DeepSeek-V4-Pro-class model, first on GB200 NVL72 racks and then on a TPU7x pod. As in the earlier applied sections, try each question with a pen before opening the answer.

Worked Problems

Our goal in this section is to apply the rooflines of the last three sections to a very practical problem: a real production deployment, as Section 8 did for LLaMA 3-70B on TPU v5e. We’re lucky here, because in March 2025 DeepSeek published a day’s worth of statistics from its production system for V3 and R1 (parallelism, node counts, tokens per second per node, daily token volumes and daily cost), so for once we get to check our arithmetic against a frontier-scale system. As in the previous “applied” sections, we’ve hidden the answers so you can try each one first. Try grabbing a pen and doing it by hand.

What Does DeepSeek Serve, and How?

Let’s remind ourselves what DeepSeek-V3 looks like (it’s the same model we worked through in Section 13):

hyperparam value
$L$ (layers; 3 dense, 58 MoE) 61
$D$ 7,168
$E$ routed experts, $k$ active, shared 256, 8, 1
$F$ (expert width) 2,048
$N$ heads (MLA) 128
KV latent per token per layer (elements) 512 + 64
$V$ 129,280
Total / active parameters 671B / 37B

DeepSeek serves it on H800 nodes, i.e. 8 GPUs with 80GB each, 200GB/s of one-way NVLink egress per GPU (half the 400GB/s bidirectional figure NVIDIA quotes, and DeepSeek measures about 160 of it in practice) and one 400Gb/s, i.e. 50GB/s, InfiniBand NIC per GPU. Here’s what DeepSeek reported for the 24 hours ending noon on February 28, 2025:

  • Prefill: the routed experts are 32-way expert parallel and attention and the shared expert are 32-way data parallel, over 4 nodes. There are 32 redundant routed experts, so each GPU holds 9 routed experts plus the shared expert, and two micro-batches are overlapped.
  • Decode: the routed experts are 144-way expert parallel and attention and the shared expert are 144-way data parallel, over 18 nodes. Again there are 32 redundant experts, so each GPU holds 2 routed experts and the shared expert. Attention is split into two steps and run in a five-stage pipeline so that communication overlaps with compute.
  • Precision: fp8 for the matmuls and the dispatch, bf16 for the attention core and the combine.
  • Load: 278 nodes at peak and 226.75 on average. 608B input tokens, of which 342B (56.3%) hit the prefix cache (which DeepSeek keeps on disk), and 168B output tokens. The average output speed was 20 to 22 tokens per second per user, and the average context length per output token was 4,989.
  • Throughput: about 73.7k input tokens per second per node in prefill (counting cache hits) and about 14.8k output tokens per second per node in decode.
  • Cost: at $2 per GPU-hour, $87,072 per day. Billed at R1’s prices ($0.14, $0.55 and $2.19 per million cache-hit, cache-miss and output tokens), the day’s tokens would have been worth $562,027.

You’ll notice that quite a few of these numbers follow from the last three sections. Let’s check.

Question: Why does DeepSeek use data-parallel attention and expert-parallel experts, rather than the tensor parallelism Section 8 used?

Click here for the answer.

There are two reasons, one from Section 13 and one from Section 14. First, MLA caches a single 576-element latent per token per layer, which all 128 heads read. If we tensor-parallelized over heads we’d have to replicate that latent on every shard, so we’d save no KV memory or bandwidth at all, whereas data-parallel attention keeps one copy per sequence. Second, our model is 671GB of fp8 weights, 656GB of which is experts, which simply can’t fit on a node, so we have to shard the experts somehow, and expert parallelism is the sharding that moves activations rather than weights. The shared expert runs for every token, so we replicate it alongside attention. The GLM-5 report puts the attention half of this nicely: “DP-attention is primarily introduced to prevent copying KV across different ranks.”

Question: How large is the KV cache per token, and per sequence at the average context of 4,989 tokens?

Click here for the answer.

Per token, we have 61 * 576 = 35,136 elements, or 35kB per token in fp8. (DeepSeek says the attention core runs in bf16 but not how the cache is stored, so we’ll assume fp8, which its FlashMLA kernels support, and note where bf16 would matter.) At 4,989 tokens that’s 175MB per sequence. For comparison, LLaMA 3-70B at its 164kB per token would need 164e3 * 4989 = 818MB at the same context, and LLaMA 3-405B (126 layers, 8 KV heads) would need 1.3GB. So MLA is buying us a lot here.

Question: Under 144-way expert parallelism with 2 routed experts per GPU, how many bytes of weights does each decode GPU hold, and how much HBM is left over for KV cache?

Answer

Let’s start with the routed experts: 2 * 3 * 7168 * 2048 * 58 = 5.1e9 parameters, so 5.1GB in fp8. Then there’s everything replicated on every GPU: attention (11.4B parameters), the shared experts (58 * 3 * 7168 * 2048 = 2.6B), the dense MLPs (1.2B) and the embeddings (1.9B), about 17GB in fp8. That gives us about 22GB per GPU, leaving 58GB of the 80GB for KV cache, activations and communication buffers. Note that about three quarters of the per-GPU weight bytes are the replicated part. This is a little counterintuitive: we went to expert parallelism to shard the experts, and it worked so well that the attention stack we copy onto every GPU now takes up more memory than the experts do.

Question: How many sequences is each decode GPU actually serving at once? Is it limited by KV memory?

Click here for the answer, once you’ve thought about it!

14.8k tokens per second per node is 14.8e3 / 8 = 1,850 per GPU. At 20 to 22 tokens per second per user, that’s about 88 concurrent sequences per GPU. At 175MB each they take up 15GB of our KV cache. If we allow 10GB for activations and buffers, there’s room for about 270 sequences, so we’re not memory-limited here, at least at the average context length. Something else is capping our batch at 88. Any guesses?

Reconstructing the Decode Step

Now let’s reconstruct the step time from the roofline and see how close we get.

Question: What is the decode step time, and how does the Section 7 roofline account for it? Assume 88 sequences per GPU at 4,989 tokens of context, fp8 weights, 3.35e12 bytes/s of HBM and 1.98e15 fp8 FLOPs/s. Assume one token per sequence per step, since DeepSeek doesn’t say whether production decode used multi-token prediction. If it did, at the V3 paper’s 1.8 tokens per step, the step would be about 86ms with 160 tokens through the MoE, and everything below scales accordingly.

Click here for the answer.

Twenty-one tokens per second per user means a step every 48ms. Let’s break the roofline into pieces:

Component Calculation Time
Weight bytes 22e9 / 3.35e12 6.6ms
KV bytes 88 * 175e6 / 3.35e12 4.6ms (9.2ms if the cache is bf16)
MoE FLOPs 88 * 2 * 37e9 / 1.98e15 3.3ms
Attention FLOPs (absorbed MLA, bf16 core; Section 14’s $2N(d_c + d_v)$ per token per position) 88 * 61 * (2 * 128 * (576 + 512)) * 4989 / 0.99e15 7.5ms

Even if we add everything up with no overlap at all, our roofline only gives us about 22ms. But the measured step is 48ms! So we’re missing more than half the step, and none of the terms in Section 7’s formula can account for it. Can you guess what it is? Try to think about it before opening the next answer.

Question: What is missing? Hint: count the MoE layers, and look at what crosses the network in each one.

Click here for the answer.

It’s the AllToAlls! Each of the 58 MoE layers does a dispatch and a combine across 144 GPUs on 18 nodes over InfiniBand, and Section 7’s formula has no term for the network at all. Per GPU per layer, we have 88 tokens times 8 experts times 7,168 elements, which is 88 * 8 * 7168 = 5.0MB of fp8 dispatch and, since the combine sums in bf16, 10.1MB of combine. All of it has to leave through the GPU’s 50GB/s InfiniBand port, and DeepSeek’s own DeepEP benchmarks show its decode kernels reaching about 39 to 40GB/s of that at 128- to 256-way EP. So we expect each MoE layer to spend 15.1e6 / 40e9 = 0.38ms on the network, and the step to spend 58 * 0.38 = 22ms.DeepEP's low-latency table gives 192µs for dispatch and 365µs for combine with a 128-token batch, which works out to 7.3MB and 14.7MB at 38 to 40GB/s. In other words the kernels are running at the NIC's bandwidth, so we can just scale the times to our 88 tokens. At these message sizes the fixed latency of a hop is a few tens of microseconds, so it isn't the dominant term. If we add the 22ms of roofline work back on, we’re at 44ms against the measured 48. Not bad! Since DeepSeek’s five-stage pipeline overlaps the two micro-batches’ attention and MoE with each other’s communication, our un-overlapped sum should if anything exceed the measured step. Falling 4ms short tells us the roofline is still missing something (kernel launches and synchronization, the router and gating, load imbalance across the experts, or a bf16 rather than fp8 KV cache, which on its own would add 4.6ms).

So roughly half of DeepSeek-V3’s production decode step is spent waiting on the expert AllToAll over InfiniBand, and only the other half on HBM bytes and FLOPs. This shouldn’t surprise us too much, since it’s exactly what Section 13’s expert-parallel roofline told us to expect: at 50GB/s per GPU, the cross-node AllToAll is communication-bound for 2,048-wide experts by about 10x with the fp8 matmuls this deployment runs (and 5x even with bf16 matmuls). The expert matmuls have no hope of hiding that much communication, so it just shows up as wall-clock time.

Why do we care? Because once we know the AllToAll is half the step, several of DeepSeek’s design choices stop looking arbitrary. Remember our earlier puzzle about why the batch per GPU is 88 rather than 270? The 20 to 22 tokens per second per user target fixes the step at about 48ms, and 22ms of that is network. If we went to 270 sequences, the bytes and FLOPs terms would triple and the per-user speed would halve, so that’s about as many as the latency target allows. It also tells us why the deployment uses 144-way EP rather than the 320-way the V3 paper originally designed: 2 experts per GPU already makes the weight bytes small, and a smaller unit is easier to keep balanced and healthy. Finally, it means multi-token prediction is worth less here than you might expect. Only the 6.6ms of weight reads and the 4.6ms of KV reads are paid once per step however many tokens come out, so a second token per sequence still pays for the AllToAll, MoE and attention terms, which all scale with tokens (about 22 + 3.3 + 7.5 = 33ms more). So the second token comes at about a 30% discount, which is a long way from free.

Takeaway: for a fine-grained MoE served with wide expert parallelism over InfiniBand, about half of our decode step is the expert AllToAll: 58 layers times 15MB per GPU at 40GB/s is 22ms before any HBM bytes or FLOPs. Section 7’s decode roofline has no network term and misses it entirely, while Section 13’s expert-parallel roofline predicts it. Our batch and EP degree both follow from that number, and since the AllToAll scales with tokens per step, it also caps what speculative decoding can buy us.

Prefill, Cost, and the Shape of the Traffic

Now let’s look at prefill, and at what the day’s traffic cost.

Question: What utilization does the prefill throughput imply? Be careful about cache hits.

Click here for the answer.

We have 73.7k tokens per second per node, which is 73.7e3 / 8 = 9,200 per GPU. If all of those tokens were actually computed, we’d get 9200 * 2 * 37e9 = 6.8e14 FLOPs/s, or 34% of fp8 peak. We also have to add attention, since prefill can’t absorb the latent the way decode does, so each token’s causal attention over an average of 2,500 past tokens costs 61 * 2 * 128 * (192 + 128) * 2500 = 1.2e10 FLOPs, about 17% on top of the 7.4e10 of matmuls. But 56.3% of input tokens hit the cache and cost almost nothing, so the tokens we actually compute are only 44% of the total, and the matmul utilization on those is closer to 15%. The truth is somewhere in between, since the 73.7k averages over prefill nodes and includes cache-hit tokens at a rate DeepSeek doesn’t tell us. Either way we’re well below the 40% that Section 8 assumed for prefill, based on dense models with no AllToAll.

Question: What does a million output tokens cost DeepSeek to produce, and what did they charge for it?

Click here for the answer.

A node costs 8 * $2 = $16 per hour and produces 14.8e3 * 3600 = 53M output tokens per hour in decode, so we get $0.30 per million output tokens in raw hardware cost. R1 was priced at $2.19, about seven times our number, which is where DeepSeek’s reported “545% cost profit margin” comes from ($562K of theoretical daily revenue against $87K of cost). The actual margin was lower, since V3 was priced below R1, the app was free, and nighttime traffic was discounted. Still, $0.30 of hardware per million tokens is a lot cheaper than most people guessed a 671B-parameter model could be served for in early 2025.

For reference, DeepSeek-V4-Pro’s list price is $3.96 per million output tokens at peak and half that off-peak (as of mid-September 2026 DeepSeek has been routing V4-Pro traffic to V4.1-Flash at $1.20 while V4.1-Pro is pending). The GB200 deployment we’ll work out below produces a V3-class token for about $0.22 of hardware at 2026 on-demand rates. If we measure against that machine instead, R1’s 2025 price of $2.19 would be about a 10x markup, and V4-Pro’s $3.96 (for a heavier 49B-active model) about 18x, compared with the roughly 7x DeepSeek had on its own H800s at $2. So the hardware cost per token went down, but the markup went up even faster, which is worth keeping in mind when you compare API prices across years.

Question: Section 8 found that a chat workload of 8k input and 512 output tokens needs three prefill servers per decode server. Using DeepSeek’s daily volumes, what is the ratio for this workload?

Click here for the answer, once you’ve thought about it!

Note that DeepSeek’s 73.7k input tokens per node-second is quoted including cache hits, so we send all 608B input tokens through it: 608e9 / 73.7e3 = 8.2M node-seconds, or 95 node-days. The 168B output tokens at 14.8k per node-second are 168e9 / 14.8e3 = 11.4M node-seconds, or 131 node-days. So decode needs 1.4 times the node-time of prefill, and the ratio from Section 8 has reversed. What changed? First, reasoning models produce long outputs (168B output against 608B input is 0.28 output tokens per input token, against 0.06 for the chat workload in Section 8). Second, prefix caching made more than half of the prefill nearly free, letting a node clear 73.7k tokens per second. As a sanity check on our bookkeeping, 95 + 131 = 226 node-days of work against an average of 226.75 nodes in service. That isn’t an independent prediction (DeepSeek’s two throughput figures are just daily totals divided by node-time), but it does confirm they were computed the same way and that we’ve split the fleet correctly.

This is probably the biggest change to the serving picture since Section 8: most of our node-time now goes to decode, and most of the attention redesigns in Section 14 are basically about making decode cheaper.

Question: DeepSeek-V3.2-Exp swapped V3’s attention for DeepSeek Sparse Attention (DSA), i.e. top-2,048 selection over an indexer (Section 14). When it shipped, DeepSeek also cut its API prices by half. Say we’re serving at the average context of 4,989 tokens. How much does DSA save us in the decode step above? Can you see why the price cut might still make sense?

Click here for the answer.

At our average context of 4,989 tokens, selecting the top 2,048 cuts the core attention reads and FLOPs by 1 - 2048 / 4989 = 59%, but the indexer adds its own read of 128 bytes per token per layer, so the net saving in KV bytes is 37%. Per sequence, our KV bytes read fall from 175MB to about 61 * (4989 * 128 + 2048 * 576) = 111MB, and the attention FLOPs from 7.5ms to about 4ms per step in the table above. Against our step of 22ms of AllToAll and 11ms of weight and KV reads, that’s a fairly minor saving.

So where does the saving come from? Long requests! Let’s say a request has 128k tokens of context. With full MLA we read 4.6GB of KV per token, while with DSA we read only 1.1GB and do 13x fewer attention FLOPs. There aren’t many requests like that, but under full attention the cost per token grows with the context, so they account for a surprisingly large share of the cost. If you look at DeepSeek’s published cost-versus-position plots, you’ll see exactly this curve being flattened, which is what lets them charge one flat per-token price. Long requests are also becoming more common, e.g. coding agents that keep hundreds of thousands of tokens of repository in context and append a few hundred tokens per step. (Footnote that follows is unchanged.)A 2026 study of coding-agent traces found that about 96% of prompt tokens were served from the prefix cache, and that a median step read back 126k cached tokens while appending 857 and generating 252. A step like that is almost entirely attention over cached context (exactly the cost DSA and V4's compression go after), and almost none of it is prefill or MoE FLOPs.

Takeaway: for DeepSeek’s measured 2025 traffic, decode needs about 1.4 times the node-time of prefill (the inverse of Section 8’s chat-era ratio), and the two published throughput figures reproduce the average fleet size exactly. Long reasoning outputs (0.28 output tokens per input token) and a 56% prefix-cache hit rate are what caused it. You’ll notice sparse attention barely helps our average 5k-token request. What it buys us is a flatter cost curve for long-context requests, and that’s where most of the cost is.

The Same Model on a GB200 NVL72

So far we’ve been on the H800, which is 2023 hardware with an 8-GPU NVLink domain. The GB200 NVL72 puts 72 GPUs, 13.4TB of HBM and 65TB/s of NVLink egress (130TB/s bidirectional, as NVIDIA quotes it) into a single rack. Let’s see what that changes for us.

Question: Say we run 64-way expert parallelism inside a single NVL72 rack. How many bytes of weights does each GPU hold with fp8 experts? With fp4 experts? Is the AllToAll compute-bound?

Click here for the answer.

Let’s start with the routed experts: 656e9 / 64 = 10.3GB in fp8 or 5.1GB in fp4, plus the same 17GB of replicated attention, shared expert, dense and embedding weights in fp8. Call that roughly 27GB with fp8 experts or 22GB with fp4 experts, out of 186GB per GPU, which leaves us about 160GB for KV cache. That’s plenty of room!

Is the AllToAll compute-bound? From Section 13, expert parallelism is compute-bound when $F > \alpha / 2$ with fp8 dispatch, where $\alpha = C / W_\text{NVLink}$. For the GB200 that’s 2.5e15 / 9e11 = 2,780 in bf16, so we get a threshold of 1,390, which V3’s 2,048-wide experts clear. But SGLang’s deployment below runs fp8 attention and fp4 experts, and at those rates $\alpha$ is 5,560 or 11,100 and the thresholds 2,780 and 5,560. So even inside the rack our AllToAll is 1.4x to 2.7x communication-bound. So the rack changes how long the AllToAll takes, but not whether it’s hidden.

How long does it take? At the bandwidth NVIDIA’s own kernels reach on an NVL72 with large batches (about 80% of 900GB/s), our 15MB per GPU per layer that took 0.38ms over InfiniBand would take 15.1e6 / 700e9 = 22µs. But at DeepSeek’s 88 tokens per GPU the kernels are actually latency-bound. TensorRT-LLM’s measurements on a GB200 NVL72 at 64-way EP give about 29 to 42µs for the dispatch and 38 to 45µs for the combine at 64 to 128 tokens per GPU, with dispatch floors of 18µs at 8-way EP and 20 to 29µs at 64-way, and a 31µs combine floor, none of which shrink with fewer bytes. Let’s say roughly 65 to 90µs per layer, so our 22ms per step becomes 4 to 5ms. That’s a 5x saving rather than the 18x the bandwidth ratio promises, since at decode batch sizes the NVLink AllToAll is limited by latency, while the InfiniBand one was limited by bandwidth.

Question: SGLang reported 13,386 output tokens per second per GPU for DeepSeek-V3 on a GB200 NVL72 with fp8 attention and fp4 experts (NVIDIA’s NVFP4 format) at 2k-token inputs. How does that compare with DeepSeek’s H800 production number, and what explains the gap?

Click here for the answer.

DeepSeek’s 14.8k per node is 1,850 per GPU, so we’re looking at 7.2x per GPU. Some of that is the benchmark rather than the hardware: 2k tokens of context instead of 5k, and no 20-tokens-per-second-per-user constraint, so SGLang could run a much larger batch. SGLang’s own EP72 deployment on H100s reached 2,800 tokens per second per GPU on the same 2k-input workload at 256 sequences per GPU (about 11 tokens per second per user), and 2800 / 1850 = 1.5, so about 1.5x of the 7.2x is workload. That leaves 4.8x to explain. Roughly half of it is just the better GPU: the GB200 has 2.4x the HBM bandwidth (8e12 against 3.35e12), 2.5x the fp8 FLOPs, and we’re running the experts in fp4. Where does the other half come from? The NVLink domain! The AllToAll stays on NVLink instead of crossing 18 nodes of InfiniBand, so the 22ms per step becomes the 4 to 5ms we just found, and we can grow the batch per GPU into the 186GB.

Can we check this? Luckily, there’s a measurement that holds the per-user speed fixed and only changes the domain: at 125 tokens per second per user, a GB200 NVL72 running 32-way EP delivered 4,130 tokens per second per GPU, against 941 for B200s in 8-GPU nodes with EP confined to the node (DeepSeek-R1 in fp4 in both cases). That’s a 4.4x difference between two GPUs with nearly identical compute, so the NVLink domain really is doing the work here!

What does this work out to in dollars? Let’s take $10.50 per GB200-hour, which is CoreWeave’s on-demand rate in September 2026 (other clouds quote $16 and up, and reserved deals start around $8). Then 13,386 tokens per second is 10.5 / (13386 * 3600) * 1e6 = $0.22 of hardware per million output tokens, or somewhere between $0.17 and $0.33 depending on which rate you use. That’s a bit cheaper than the $0.30 we found for the H800 at DeepSeek’s assumed $2, although we should remember that the benchmark isn’t paying the per-user speed target, which we saw cost DeepSeek a factor of 1.5 in batch.

Takeaway: moving a fine-grained MoE from 8-GPU nodes over InfiniBand to a 72-GPU NVLink domain buys us about 2x to 4x in decode throughput per GPU at equal silicon, mostly at tight per-user latency targets (4.4x at 125 tokens per second per user in the GB200-against-B200 measurement above). Once we include the GPU upgrade and a looser latency target, it’s about 7x against DeepSeek’s H800 production figure. This is what Section 13 meant by treating the rack (rather than the node) as the unit of MoE serving.

Training a V4-Class Model on GB200 NVL72 Racks

Now let’s say we wanted to train a model of this class instead of serving one. DeepSeek-V4-Pro is 1.6T total parameters, 49B active, 384 experts of width 3,072 with 6 active per token, 61 layers, trained on 33T tokens with a batch that ramps to 94.4M tokens, in fp8, with Muon (Section 15’s optimizer, which needs 6 rather than 10 bytes of state per parameter).

What hardware should we plan for? Annoyingly, DeepSeek doesn’t tell us what it trained on, and neither do Kimi, Zhipu or Qwen for their 2026 models. About the only 2026 frontier runs that name their machine are NVIDIA’s own Nemotron 3 Super and Ultra, whose long-context phases ran on GB200 GPUs (presumably NVL72 racks, since Ultra’s 128-way expert parallelism doesn’t fit in a smaller domain, although the main phases’ hardware isn’t stated), and the most recent non-NVIDIA run we know of that did was Mistral Large 3 in December 2025, on 3,000 H200s. So we’ll have to guess. Let’s plan the run on the machine a well-funded GPU lab would most likely use: 128 GB200 NVL72 racks, i.e. 9,216 GPUs, each with 186GB and 8e12 bytes/s of HBM, 5e15 fp8 FLOPs/s, 900GB/s of NVLink egress to every other GPU in its rack, and one 400Gb/s (50GB/s) InfiniBand NIC out of the rack, for 3.6TB/s of egress per rack.

Section 12’s intensities in fp8 are then 5e15 / 900e9 = 5,560 over NVLink and, if we take the rack’s 3.6TB/s of InfiniBand egress as Section 12’s $W_\text{collective}$ for anything gathered across racks, 5e15 / 3.6e12 = 1,390 for FSDP (fully sharded data parallelism, Section 5’s weight-gathering data parallelism).

Question: How many FLOPs is our run, and how long does it take us at 40% utilization of fp8 peak?

Click here for the answer.

We have 6 * 49e9 * 33e12 = 9.7e24 FLOPs. Our cluster delivers 9216 * 5e15 = 4.6e19 FLOPs/s at peak, so at 40% our run takes 9.7e24 / (4.6e19 * 0.4) = 5.3e5 s, or 6.1 days. At the 17% (19% counting attention FLOPs) that DeepSeek achieved for V3 on H800s (Section 15) it would take us 14 days. For comparison, DeepSeek-V3’s 3.3e24 FLOPs took about 54 days on 2,048 H800s (2.664M GPU-hours), and our run on that cluster at that efficiency would take 9.7e24 / (2048 * 1.98e15 * 0.17) = 1.4e7 s, or 163 days. So there’s no way DeepSeek could have trained a V4-class model on its V3 cluster in any reasonable time. On 2,048 GB200s at 40% it would take us 27 days, which is more like it. Since our 128-rack GB200 cluster is roughly a 10x larger machine than DeepSeek’s V3 cluster in fp8 FLOPs, a 2026 frontier open model is only about a week of compute on it. That’s great, but a week of compute is only a week if we can actually keep the chips busy, so let’s look at how we’d shard this.

Question: What parallelism plan does Section 13 recommend, and are we compute-bound?

Click here for the answer, once you’ve thought about it!

Our batch is 94.4M tokens over 9,216 GPUs, so we have 10,200 tokens per GPU. Pure FSDP across racks would need (384 / 6) * 1390 = 89,000 tokens per GPU with bf16 weight gathers, about nine times what we have, so that’s basically ruled out, as Section 13 predicted.

Instead, let’s put the expert parallelism inside the rack, with 72-way EP, one group per rack384 experts over 72 GPUs is five or six per GPU. That's fine for a grouped-matmul kernel, and Kimi K3's training system would make it six each by adding redundant copies of the hottest experts. You could also run 64-way EP on 64 of the rack's GPUs and give the other 8 the redundant copies, as DeepSeek's serving system does. The arithmetic below barely changes either way., and FSDP across the 128 racks.

Our FSDP threshold then becomes (384 / (6 * 72)) * 1390 = 1,240 tokens per GPU with bf16 gathers, or 620 with fp8 gathers, against our 10,200: compute-bound with an 8x margin. What about the expert AllToAll inside the rack? It needs $F > \alpha_\text{fp8} / 2 = 5560 / 2 = 2{,}780$ with fp8 matmuls, fp8 dispatch and bf16 combine, and V4-Pro’s experts are 3,072 wide, so we’re compute-bound by 10% without any overlap at all, at the spec 900GB/s. At the 700 to 730GB/s that NVIDIA’s and DeepSeek’s kernels actually reach on Blackwell NVLink with large batches, $\alpha$ is about 7,000, the threshold about 3,500, and V4-Pro’s experts miss by 10 to 15%. (DeepSeek’s own condition for hiding the AllToAll behind expert compute, $C / W \leq 2F = 6{,}144$ FLOPs per byte, is met at spec bandwidth and needs 90% of it in practice.) So we still have a little margin here, but not a lot. To be safe we’d want to overlap the AllToAll with attention or with a second micro-batch, which is exactly what DualPipe-style schedules give us.

On paper, then, nothing in our plan is communication-bound by more than a few percent, and we don’t need the heavy overlap gymnastics of Section 13. So what does set our utilization? The pipeline (we don’t need it for memory, but more or less every published run uses it to keep the data-parallel axis small and interleave micro-batches), the attention layers, the HBM traffic of the sparse-attention indexer, and how close the grouped expert matmuls get to peak with 10,200 tokens spread over five or six experts per GPU.

Note [keep the EP group inside the rack]: be careful here, since this plan only works because the AllToAll never leaves NVLink. If an EP group spills into a second rack, its bandwidth drops from 900GB/s to 50GB/s per GPU (an 18x loss.), and if we had a cluster of 8-GPU HGX B200 nodes instead of racks, the AllToAll would run over InfiniBand at $\alpha_\text{fp8} = 90{,}000$, where basically nothing is compute-bound.

Question: How much memory does our run need per GPU for weights and optimizer state, and for activations?

Answer

Let’s do weights and Muon state first: our 1.6T parameters at 6 bytes each (Section 15) is 9.6TB, sharded over the whole cluster, so 1GB per GPU. With fp32 master weights and fp32 gradient accumulators as in DeepSeek’s recipe, we add 8 bytes per parameter, another 1.4GB per GPU, for 2.4GB in total. Now for activations: our 10,200 tokens per GPU times 61 layers times a few checkpoints of width 7,168 in bf16 is 10200 * 61 * 7168 * 2 * 4 = 36GB with four checkpoints per layer, out of 186GB. So memory is basically a non-issue at this scale, exactly as Section 6 found for LLaMA 3-70B and Section 13 predicted. (On 2,048 GPUs the same run would have 46,000 tokens per GPU and the activations would grow to 160GB, so a smaller cluster needs pipeline parallelism or more checkpointing to fit, as DeepSeek-V3’s did.)

Takeaway: a 2026 frontier MoE is about a week of pretraining on 128 GB200 NVL72 racks at 40% utilization. Our plan is expert parallelism of about $E/k$ inside each rack, where NVLink keeps the AllToAll within about 10% of compute-bound for 3,072-wide experts even in fp8, and FSDP or data parallelism across racks, where the rack’s 3.6TB/s of InfiniBand egress makes the weight gathers cheap. Memory is irrelevant at this scale, and the rooflines say nothing is communication-bound by more than a few percent. For comparison, the same model on 2,048 H800s at DeepSeek-V3’s efficiency would take us about five months.

The Same Run on a TPU7x Pod

Now let’s say that instead we had a full TPU7x (Ironwood) pod: 9,216 chips, 192GB and 7.4e12 bytes/s of HBM each, 4.61e15 fp8 FLOPs/s, and a 3D torus with 1.8e11 bytes/s per axis, so $\alpha = C / W_\text{ici}$ is 2.3e15 / 1.8e11 = 12,800 per axis in bf16 and 25,600 in fp8. The pod delivers 9216 * 4.61e15 = 4.2e19 FLOPs/s at peak, so at 40% our run takes 9.7e24 / (4.2e19 * 0.4) = 5.7e5 s, or 6.6 days, within 10% of the GB200 cluster. So the FLOPs are more or less a wash, and the difference is in what the network lets us do.

Question: What parallelism plan does Section 13 recommend on the pod, and are we compute-bound?

Click here for the answer.

Our batch is 94.4M tokens over 9,216 chips, so again we have 10,200 tokens per chip. If we tried pure FSDP we would need (384 / 6) * 25600 / 3 = 546,000 tokens per chip with fp8 FLOPs and bf16 gathers, about fifty times what we have, so we can rule that out straight away.

Instead, let’s take 64-way expert parallelism on a 4x4x4 cube (so the longest EP axis is $A = 4$) and FSDP over the remaining 144. Our FSDP threshold becomes (384 / (6 * 64)) * 25600 / 3 = 8,500 tokens per chip with bf16 gathers (4,270 with fp8 gathers), and we have 10,200. So we’re compute-bound with a little margin, but only if the FSDP gathers get all three axes to themselves while the AllToAll runs elsewhere in the step. If the two have to share links, we lose that margin.

What about the expert AllToAll? It needs $F > A \alpha / 8 = 4 \cdot 25600 / 8 = 12{,}800$ with fp8 FLOPs and fp8 dispatch, and V4’s experts are only 3,072 wide, so our AllToAll is 4x communication-bound if nothing overlaps it. DeepSeek’s own condition for hiding the AllToAll behind expert compute, $C / W \leq 2F = 6{,}144$ FLOPs per byte, isn’t met by TPU7x’s per-axis 25,600 in fp8 either. So our plan is 64-way expert parallelism and 144-way FSDP, and the AllToAll has to be overlapped with attention and the shared expert, as every training layout in Section 13 does. If we didn’t overlap it at all, the MoE layers (about 60% of active FLOPs) would run 4x slow and the step would take 0.4 + 0.6 * 4 = 2.8x its compute-bound time, taking our utilization from 40% down to about 14%. That range, 14 to 40%, nicely brackets the 17 to 19% DeepSeek-V3 achieved on H800s (Section 15). Memory is the same non-issue as on the GPU cluster (1GB of weights and optimizer state per chip, 36GB of activations). So unlike the GB200 cluster, where nothing was really holding us back, here the ICI limits us.

Question: DeepSeek-V3.2 says its RL budget exceeded 10% of pretraining. If a V4-class run spends 10% of its FLOPs on RL, how many tokens are generated, and how long does it take us on either machine if decode runs at 10,000 tokens per second per accelerator? Every generated token is also trained on. (Is that reasonable? DeepSeek’s production H800s manage 1,850 per GPU under a per-user latency target, and SGLang’s GB200 benchmark hits 13,400 without one. Our training cluster has no users to serve, so 10,000 is on the generous side but not crazy.)

Click here for the answer.

10% of our 9.7e24 is 9.7e23 FLOPs. Each generated token costs 2 * 49e9 FLOPs to generate and 6 * 49e9 to train on, so 8 * 49e9 = 3.9e11 in all, so the budget buys us about 2.5 trillion generated tokens, roughly 8% of the pretraining corpus, produced one token at a time. At 10,000 tokens per second per accelerator our 9,216-way machine generates 9.2e7 tokens per second and needs 2.5e12 / 9.2e7 = 27,000 s, or about 7.5 hours, if every accelerator decoded at full rate the whole time. So the FLOPs aren’t what we should worry about. The problem, as we saw in Section 15, is that generation runs at a fraction of the pod’s efficiency and can’t finish before its longest response does, so the calendar time ends up several times the FLOPs time.

Takeaway: the same run on an Ironwood pod takes us the same week at the same utilization, with the same plan of expert parallelism of about $E/k$ plus FSDP over the rest. The difference is that on the pod the expert AllToAll is 4x communication-bound and has to be hidden behind attention, since TPU7x’s ICI didn’t grow along with its FLOPs the way a GB200’s NVLink did. The RL phase that follows generates a few trillion tokens at decode speed on either machine.

Worked Problems

Let’s finish with a few problems to try yourself.

Question 1 [Kimi K3 on H20s]: Say we want to serve Kimi K3 on H20s. It’s 2.8T parameters, 104B active, with 24 MLA layers (a 576-element latent) and 69 Kimi Delta Attention layers (217MB of bf16 state per sequence), and its shipped weights are 1.56TB with fp4 experts. The H20 is the Hopper GPU NVIDIA sells in export markets, with 96GB of HBM, about 148 bf16 and 296 fp8 TFLOPs/s, 450GB/s of one-way NVLink (900 bidirectional) and one 400Gb/s InfiniBand NIC per GPU. Note that its arithmetic intensity is only about 37, so it’s memory-bound on basically everything, which is actually what you want for decode. If we use 128-way expert parallelism over 16 nodes, how many bytes of weights does each GPU hold? How many 128k-token sequences fit per GPU? At 100 sequences per GPU, how many bytes does each of the 92 MoE layers’ AllToAlls move per GPU (16 active experts, a 3,584-wide latent, fp8 dispatch and bf16 combine), how long does that take at 40GB/s, and what does that imply for tokens per second per user without speculation?

Question 2 [prefill-decode ratio for an agent]: Say a coding agent keeps 200k tokens of repository in context, appends 1k tokens per step, generates 300 tokens per step, and takes 50 steps per task, with a 96% prefix-cache hit rate. For DeepSeek-V3 (full MLA) and V3.2 (DSA), compute the bytes read from HBM per step for attention, the prefill FLOPs per step, and the ratio of decode to prefill node-time. How does it compare with the 1.4:1 we measured for DeepSeek’s overall traffic?

Question 3 [DSA at the tail]: Using Section 14’s formulas, compute the decode step time we’d expect for DeepSeek-V3 and V3.2 at 88 sequences per GPU when the context is 128k rather than 5k, on an H800, including the 22ms of AllToAll time. Which term dominates in each case?

Question 4 [Ironwood versus NVL72 for serving]: Say we have a 4x4x4 TPU7x cube (64 chips, 192GB each, 7.4e12 bytes/s of HBM, 6 ICI links at 9e10 bytes/s one-way, so 1.8e11 per axis as above) and a GB200 NVL72 (72 GPUs, 186GB, 8e12 bytes/s, 900GB/s NVLink egress), and both hold DeepSeek-V4-Pro’s 0.87TB of fp4-expert weights. For a decode step of 128 sequences per chip at 128k context, compute our KV bytes per step using Section 14’s figure of about 100MB read per token for V4-Pro at that context, the weight bytes, and the AllToAll bytes per layer. Which system ends up bandwidth-bound, and on which resource (HBM, ICI or NVLink)? Which one has the lower latency floor, and why?

Question 5 [the fp8 gather question]: In the GB200 training plan above, the FSDP threshold across racks was 1,240 tokens per GPU if we gather the weights in bf16 and 620 if we gather them in fp8, and in the TPU7x plan it was 8,500 and 4,270 per chip. DeepSeek’s recipe keeps fp32 master weights and quantizes to fp8 per 128x128 block before each matmul. Where in the FSDP gather should the quantization happen so that the network carries fp8, and what extra memory or compute does it cost us?

Question 6 [what Section 8 got right]: Go back to Section 8’s LLaMA 3-70B serving analysis and redo the “prefill to generate server ratio” question for a reasoning workload with 8k input and 16k output tokens and a 50% prefix-cache hit rate. Then redo it for LLaMA 3-70B’s KV cache at a 128k context. Which of that section’s conclusions survive, and which were artifacts of the 2024 workload?
